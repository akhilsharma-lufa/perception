From Pixels to World Coordinates: A First-Principles Primer

This document focuses deeply on intrinsics, unprojection, frame synchronization, and pose composition. It starts from basic definitions and builds toward robotics-grade understanding.

0) The Most Basic Building Blocks

What is a viewport?

In rendering and vision, the viewport is the 2D pixel grid where an image appears. If your RGB frame is W x H, then valid pixel coordinates are: 

u in [0, W-1], v in [0, H-1]

Here u is horizontal (x-like), and v is vertical (y-like).

What is a pixel coordinate?

A pixel coordinate (u, v) is an address in the image plane, not a real-world location. To recover 3D meaning, you must combine pixel location with camera model and depth.

What is a camera coordinate frame?

The camera frame is a 3D coordinate system attached to the camera itself. A 3D point in this frame is P_cam = [X, Y, Z]^T.

  • Z: distance along camera viewing direction.
  • X, Y: lateral/vertical offsets from optical axis.

Many planes confusion: what to keep, what to ignore

In real devices there are many physical surfaces (lens cover glass, lens stack, phone display, laptop display), but for vision geometry you should keep only three model entities:

  1. Camera center (pinhole origin in the model).
  2. Image/sensor plane (pixel grid where u, v and cx, cy live).
  3. 3D scene point (where X, Y, Z live).
Phone screen and external monitor are display surfaces only; they are not geometric planes in the camera projection equations.
Symbol Lives in Meaning
u, v Image/sensor plane Observed pixel coordinates
cx, cy Image/sensor plane Principal point (optical axis intersection in pixels)
fx, fy Camera calibration parameters Pixel-space focal scales for x/y
z Camera 3D frame Depth along optical axis
X, Y, Z Camera 3D frame 3D point coordinates in camera space

Practical bridge: pixel offset chooses the ray, depth chooses where on that ray the 3D point lies.

1) What Hardware Is Sending You

For each capture instant, your iPhone + Record3D stack provides a packet with several fields:

Field Data Type / Shape (typical) Meaning Real-world interpretation
rgb Image array, e.g., H x W x 3 Color intensity per pixel Appearance/semantics: what object is there
depth Image array, e.g., H x W Distance estimate per pixel Geometry: where surfaces are in 3D
confidence Image array, e.g., H x W Quality of each depth pixel Uncertainty: how much to trust depth
intrinsics fx, fy, cx, cy (your code uses tx, ty for cx, cy) Mapping between 3D camera rays and 2D pixels Scale and center needed for all geometry math
camera_pose Quaternion + translation Camera orientation and position in world frame Lets you fuse many frames into one map
Depth unit can be meters or another scale depending on API and pipeline settings. Always verify with a known measured target distance.

1.1) What Is Verified from Library Source

The following points are verified directly from the Record3D C++/Python binding code in libs:

  • Each incoming packet contains RGB/depth/confidence dimensions, payload sizes, and device type.
  • The parser reads data in this order: header -> intrinsics -> camera pose -> RGB -> depth -> confidence -> optional misc buffer.
  • depth is exposed to Python as float32 2D array.
  • rgb is exposed as uint8 array with 3 channels.
  • confidence is exposed as uint8 2D array.
  • Intrinsic coefficients are exactly fx, fy, tx, ty.
  • Pose fields are exactly quaternion qx, qy, qz, qw and translation tx, ty, tz.
  • Device types are 0 = FaceID/TrueDepth, 1 = LiDAR.
  • API docs explicitly describe camera pose as being in world space.
Not verified in this binding: an explicit timestamp field and the exact depth unit label. Treat depth scale as a runtime calibration step.

1.2) iPhone 16 Pro Example (Concrete Interpretation)

Since you are using an iPhone 16 Pro, interpret each packet with this practical model:

  • Rear camera workflow: expect LiDAR mode for environment geometry (deviceType = 1).
  • Front camera workflow: expect TrueDepth/FaceID mode (deviceType = 0), often mirrored in demos for intuitive display.
  • RGB: textured appearance for detection/classification.
  • Depth: per-pixel surface distance estimate for geometry.
  • Confidence: quality class per depth pixel (0/1/2 in this library docs/comments).
  • Pose: camera orientation and translation in world space, used to accumulate multi-frame maps.

Same data, two operating styles on iPhone 16 Pro

Use rear LiDAR stream. Fuse depth points into a world map, confidence-gate noisy regions, and use pose to accumulate over motion.

Use front TrueDepth stream for short-range geometry and interaction tasks. Mirror correction may be needed for display only.

2) Intrinsics and Coefficients: Camera Matrix You Build

Your coefficients are converted into: 

K = [[fx,  0, cx],
     [ 0, fy, cy],
     [ 0,  0,  1]]

This matrix is the pinhole camera model in pixel units.

  • fx, fy: focal length along x/y measured in pixels.
  • cx, cy: principal point (where optical axis intersects image plane).
  • In your code tx/ty are used as principal point terms.

Projection (3D -> pixel)

[u]     [fx 0  cx] [X/Z]
[v]  =  [0  fy cy] [Y/Z]
[1]     [0  0  1 ] [1  ]

Intuition

  • Higher fx means stronger zoom in x-direction.
  • If cx, cy are wrong, all 3D reconstruction is biased sideways.
  • Using wrong intrinsics is equivalent to using the wrong ruler and origin.
Notation and camera model notes:
  • ^T means transpose. Example: [X, Y, Z]^T is a column vector.
  • fx and fy can differ due to calibration, resampling/cropping, and effective pixel scaling in the imaging pipeline.
  • Do not force fx == fy unless your calibration explicitly supports that constraint.

3) Unprojection Equation (Pixel + Depth -> Camera 3D)

If you know a pixel and its depth, you can recover 3D coordinates in camera space: 

Given pixel (u, v), depth z:
X = (u - cx) * z / fx
Y = (v - cy) * z / fy
Z = z

P_cam = [X, Y, Z]^T

Geometric meaning

  • (u - cx)/fx and (v - cy)/fy give a normalized camera ray direction.
  • Multiplying by depth z scales that ray to an actual 3D point.
  • Do this for all pixels with valid depth -> dense point cloud.
In robotics this is the bridge from image-space perception to physically actionable geometry.

4) Frames, Synchronization, and Why It Matters

What is a frame?

A frame is one snapshot at one time t. In RGB-D systems you usually want: rgb(t), depth(t), confidence(t), pose(t), intrinsics(t) aligned to the same time.

Why synchronization matters

If RGB and depth come from slightly different times while camera/object moves, the same pixel no longer corresponds to the same physical surface point. This creates 3D errors, wrong object distances, and unstable mapping. 

Bad case:
  rgb from t0
  depth from t0 + dt
  pose from t0 + 2dt
  --> inconsistent geometry

Good case:
  coherent packet from same timestamp window
  --> stable 3D interpretation

Practical synchronization model

  • Attach timestamp to each sensor channel.
  • Use bounded queue and choose nearest timestamp match.
  • Drop stale packets if processing lags.
  • Measure end-to-end latency and frame age continuously.

5) Coordinate Frames and Pose Composition

Core coordinate systems

  • Image frame: pixel coordinates (u, v).
  • Camera frame: local 3D coordinates (X, Y, Z) tied to lens/sensor.
  • World frame: persistent global reference used for maps and robot planning.

Pose format from hardware

  • Quaternion (qx, qy, qz, qw) encodes camera orientation.
  • Translation (tx, ty, tz) encodes camera position in world coordinates.
  • Together they define rigid transform T_world_cam.
P_world = R_world_cam * P_cam + t_world_cam

So once you unproject a depth pixel into P_cam, pose lets you place that point in a global map.

Composition with AprilTags (preview)

T_world_tag = T_world_cam * T_cam_tag

This equation anchors detected tags into world space and is the basis for map alignment, relocalization, and robot coordinate handoff.

6) What These Values Mean in the Real World

Frames

A frame is a measurement event. For robotics control, frame age (latency) matters as much as frame rate. Old but high-fps data can still destabilize control.

Pose

Pose tells where the camera is and how it is rotated. If pose drifts, your world map drifts. If pose jumps, your map can tear unless smoothed and validated.

Synchronization

Synchronization tells if each data field refers to the same moment. Poor sync causes geometry mismatch and wrong distances, especially during motion.

Intrinsics

Intrinsics are your camera ruler and center offset. If they are wrong, every 3D coordinate you compute is systematically wrong.

7) Minimal Mental Model to Keep Forever

  1. Pixel (u,v) alone is 2D address, not a 3D point.
  2. Add depth z and intrinsics K -> you get P_cam.
  3. Add pose T_world_cam -> you get P_world.
  4. Do this at every synchronized frame -> you get a stable 3D map over time.
Most major RGB-D bugs are either (1) wrong units, (2) wrong transform direction, or (3) unsynchronized channels.
